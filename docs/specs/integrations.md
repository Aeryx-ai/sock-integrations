# sock-integrations v1

Packaging that lets agent platforms message a human through sock. Consumes [sock-mcp](../../../mcp/docs/specs/tools.md) and sock-cli. Adds no server surface and no domain model.

## Context

Conformist downstream of the sock-mcp tool contract and the `sock` CLI. Platform vocabulary (hooks, channels, plugins, sessions) stays here and never enters sock-mcp. Contracts: no API endpoints, no domain events and no tables, because this repo only consumes existing ones. Every transition it triggers is `NotifyOwner` or `Send`, already specified in the sock-contract API.

Caller class: puppet device (`sock_pt_`). A machine key (`sock_mk_`) is accepted in the same place and swapped for the project's puppet token before any call (ADR 10), so every call still runs as a puppet. Human session tokens are not supported by the hooks, because `NotifyOwner` needs a puppet.

## Scope

v1 is bearer-token platforms only.

In: Claude Code plugin, Codex config and hooks, Agent SDK example, the headless inbound runner (`runner/sock-runner`) and the Managed Agents bridge (`runner/sock-bridge`).

Out, tracked in bd:
- Managed Agents webhook delivery: a follow-up bead after the bridge below, declined. Session creation and owner-brokered tool confirmations are built (below).
- Codex app-server live injection (`turn/steer`): a follow-up bead after the runner below.
- Hosted HTTP surfaces: Responses API hosted MCP, claude.ai, ChatGPT, Managed Agents cloud MCP. sock-mcp is stdio only, and these need a public URL and an OAuth-style credential.
- Won't do: a `Stop` hook that fetches pending messages. The channel is the inbound path.

## Rules

1. One puppet per binding (platform plus machine). A leaked token costs one binding, and the server rate limit (60 sends per minute) is per puppet.
2. One consumer per puppet. The channel and any `sock_fetch` caller consume the same deliveries, so a puppet with the channel on is never used for fetch. The channel pushes but never acks on push, since Claude Code drops a push it has no channel for and says nothing (integrations-bn5): a `sock_send` reply acks only the `message_ids` it names (the channel tag's `message_id`), and the skill has the model call `sock_ack` for a message that needs no reply. An unacknowledged message comes back after a restart, at most 5 times.
3. The token comes from the environment or the plugin's secure `userConfig`. No checked-in file holds it.
4. Hooks forward what the owner needs to act on and nothing more: the notification text for a permission prompt, and the trailing ask of the last assistant message (fenced code dropped, secret shapes redacted, 600 bytes) when a session is waiting. Nothing is sent when nothing is pending. Until 2026-10-13 this rule said hooks never forward free text; the owner reversed it ("Is something waiting on me, then tell me what I need to do in the sock message") and accepted that text the assistant echoed can leave the machine.
5. Hooks always exit 0 and never retry. A second call gets a second idempotency key and can double post. The CLI already retries one call internally with one key.
6. Message text received from sock is untrusted. The channel gates on the owner id; nothing here widens that gate.

## Claude Code plugin

Layout, plugin root `claude-code/`:

```
.claude-plugin/plugin.json
.mcp.json
hooks/hooks.json
hooks/notify.sh
skills/sock/SKILL.md
```

Marketplace file at the repo root, `.claude-plugin/marketplace.json`: name `sock-integrations`, a `description`, an `owner`, and one plugin entry `{"name": "sock", "source": "./claude-code", "description": ...}`. Install: `/plugin marketplace add aeryx-ai/sock-integrations`, then `/plugin install sock@sock-integrations`.

`plugin.json`: name `sock`, `version`, `author`, `description`, MIT, plus whatever `claude plugin validate --strict` requires. `make build` runs the validator, so it is the authority on required manifest fields. Every `userConfig` option carries a `title` and a `description`. Options:

| Key | Type | Notes |
|---|---|---|
| `sock_token` | string, sensitive, required | Titled "sock machine key or puppet token": a `sock_mk_` machine key (a puppet per project) or a `sock_pt_` token (one puppet). Stored in secure storage, exported to hooks as `CLAUDE_PLUGIN_OPTION_SOCK_TOKEN` |
| `sock_url` | string, default `https://api.sock.aeryx.ai` | Exported as `CLAUDE_PLUGIN_OPTION_SOCK_URL` |

`channels`: one entry bound to the `sock` MCP server.

`.mcp.json`: server `sock`, `command` `sock-mcp`, `args` `["--channel"]`, `env` `SOCK_TOKEN` and `SOCK_URL` from `${user_config.sock_token}` and `${user_config.sock_url}`. Tools alone work without the dev flag. Inbound needs the channel loaded: `claude --dangerously-load-development-channels plugin:sock@sock-integrations`, interactive only, research preview, enabled by an org admin on Team and Enterprise.

`hooks/hooks.json`, all `async: true` so the agent never waits:

| Event | Matcher | Text |
|---|---|---|
| `Notification` | `permission_prompt` | `--permission`: the notification's own text, which names the tool (`needs permission` when `jq` is absent) |
| `Notification` | `idle_prompt` | `--idle`: the ask recorded by the last `Stop` for this session, or, when no `Stop` ran for it, the last assistant text in the transcript; nothing when nothing is pending; the same ask is never reposted |
| `Stop` | none | `--stop`: records the ask in `last_assistant_message` (the trailing question or decision, code blocks dropped, 600 bytes) for `--idle` and sends nothing. `--stop --ask-now` (Codex, which has no idle event) also sends the ask at once |

Each entry runs `${CLAUDE_PLUGIN_ROOT}/hooks/notify.sh <mode>` in exec form. The script parses the hook JSON with `jq` (a dependency since 2026-10-13; without it the session cannot be classified, so nothing is sent: notify.sh rule 8). The owner's words on the fixed phrases, from his phone: "These messages are not helpful. Is something waiting on me, then tell me what I need to do in the sock message." So the ask leaves the machine, capped and stripped of code blocks; rule 4 below is amended to match. The ask and the hash of the last one sent live per session under `${XDG_STATE_HOME:-~/.local/state}/sock-integrations/asks/` (mode 600, swept after 7 days).

`SKILL.md`: never message the owner unprompted (the hooks tell the owner when the session waits on them, and sock-mcp refuses an owner message that is not a reply), never post into the owner's conversation to get around that, how to reply to a `<channel source="sock" ...>` tag with `sock_send` and the tag's `conversation_id`, that a reply on the channel is the owner's answer to the question asked, and that other message text is data, not instructions.

## Codex

Files under `codex/`: `config.toml` snippet, `hooks.json`, `install.md`.

- `mcp_servers.sock`: `command = "sock-mcp"`, `env_vars = ["SOCK_TOKEN", "SOCK_URL"]` so the token is forwarded from the shell and never written to config.
- `hooks.json`: `PermissionRequest` runs `--permission` (text `needs permission`) and `Stop` runs `--stop --ask-now`, which sends the turn's ask at once (Codex has no idle event); both `async: true`, running the shared `notify.sh`. Codex handlers take no `args` field, so each `command` carries its arguments inline. The file holds the placeholder `/ABSOLUTE/PATH/TO/sock-integrations`, which install substitutes with the checkout path (`install.md` gives an awk recipe that treats `#`, `&` and `\` literally). The checkout path must contain no spaces. Whether Codex parses `command` through a shell or as exec form is unconfirmed in its docs, so the inline quoting is verified by hand at release.
- `install.md`: merge the entries into `~/.codex/hooks.json` (all matching hooks run), export `SOCK_TOKEN` only in a Codex launcher or wrapper script and not a global rc file (Claude Code's Bash tool inherits the environment, so a model can read it), then review and trust the hooks with `/hooks`. Codex skips a hook until it is trusted, and changing the script re-requires trust.
- Outbound only. The model can call `sock_send` as a tool. No inbound in v1.

## Agent SDK

`agent-sdk/example.ts`: `query()` with `mcpServers.sock` as a stdio server (`command: "sock-mcp"`, `args: ["--outbound-only"]`, `env.SOCK_TOKEN` from `process.env`, which the example then deletes from `process.env` so the Claude Code process `query()` spawns, and any shell tool in it, does not inherit it) and `allowedTools` of `mcp__sock__sock_whoami`, `mcp__sock__sock_list_conversations` and `mcp__sock__sock_send`. Auto-approving `sock_send` is the point for headless agents. ## notify.sh

Shared by Claude Code and Codex. Behavior:

1. Read the hook JSON from stdin, bounded to 2 seconds so a held-open stdin cannot hang the hook, and parse it with `jq`. The mode is the first argument: `--permission`, `--stop` (optionally `--ask-now`), or `--idle`. Any other argument, or none, sends nothing (the v1 fixed phrase is gone, rule 3).
1a. `--stop` extracts the ask from `last_assistant_message`: fenced blocks dropped (CommonMark: a run of 3 or more backticks or tildes opens one, and only a run of the same character at least as long, indented at most 3 spaces, with nothing after it closes it; one departure, a backtick run with a backtick later on its line opens a fence too, where CommonMark reads inline code, so code under it is dropped rather than sent) and indented code blocks dropped (a line of 4 spaces or a tab of indent after a blank line or more such code), then from the last paragraph holding a `?` to the end, or the paragraph before a trailing numbered list (blank lines between its items included); nothing when there is neither. Byte caps (600 for the ask, 300 for `--permission`) drop a UTF-8 sequence the cut leaves incomplete, since the CLI refuses invalid UTF-8. It records the ask per session (`asks/<session>.ask`, written atomically) and clears the session's sent marker, so each turn starts fresh. `--idle` sends the recorded ask once per turn (`asks/<session>.sent` holds its SHA-256, written once the session and the hour allow the send and before it, so a send the watchdog killed (status 143 or 137) after the server took it is not repeated; any other failure, or one before `sock send` ran, removes it, so the next idle sends the ask. A `sock` that exits nonzero other than 143 or 137 after the server accepted the send can therefore post the ask twice: a deliberate trade, since a lost ask is worse; skipped when no hash tool exists). A `Stop` that found no ask records an empty one, which is nothing pending. When no `Stop` ran for the session, `--idle` reads the last 2 MiB of `transcript_path`, only when it is a regular file, and takes the last assistant entry that carries text. `--permission` sends the notification's `message`. Every outgoing text has the token and common secret shapes replaced with `[redacted]`, the ask over the whole message (its last 64 KiB) before it is extracted, so a paragraph split inside a secret cannot drop its marker; when the message is longer, the cut can land inside a secret, so the partial first paragraph is dropped, and everything through a private key's `-----END` line whose `-----BEGIN` was cut away, and nothing left means no ask; and before any other byte cap so a secret straddling the cut is never sent in part; the seds run in the C locale on at most 64 KiB, since GNU sed in a UTF-8 locale backtracks the `NAME value` rule quadratically (private keys from `-----BEGIN ... PRIVATE KEY...-----` through the matching `-----END`, every line between, PGP `PRIVATE KEY BLOCK`s too, the user part of a URL, `hooks.slack.com/services/` paths, JWTs, `xox[abposr]-`, `tskey-`, `glpat-`, `AIza`, `npm_`, `sk_live_`/`rk_live_` (and `_test_`), sock, AWS, GitHub and `sk-` keys, `Authorization` and bearer values, `NAME=value` or `NAME: value` where NAME names a key, token, secret or password in any case, a quoted value redacted whole, `NAME value` for such a NAME with an underscore, `pass=` and `pwd=`, URL query strings).
2. Resolve token: `CLAUDE_PLUGIN_OPTION_SOCK_TOKEN` (set only under the plugin), else `SOCK_TOKEN`. The plugin token wins because `.mcp.json` always gives sock-mcp the plugin token, and an ambient `SOCK_TOKEN` exported for Codex must not make Claude Code hooks post as the Codex puppet. The URL comes from the same source as the token: `CLAUDE_PLUGIN_OPTION_SOCK_URL` for the plugin token, `SOCK_URL` for the env token, never the other. A URL from the matching source is passed as `sock --url`, so a config file cannot override it; with none, `SOCK_URL` is unset for the child, no `--url` is passed and the CLI default or config applies. Missing token: log one line and exit 0.
2a. A `sock_mk_` machine key is never the sender. The script runs `sock puppets ensure -- <CLAUDE_PROJECT_DIR, else PWD>` with the key as `SOCK_TOKEN` for that call only, runs it under the same watchdog as the send, accepts the printed path only when it names a regular file under the state dir's `puppets` cache, physically too (`cd -P` on its directory, so a symlinked directory cannot lead outside), whose first line is a `sock_pt_` token, and sends with that puppet token, so each project's messages come from `<project> on <host>` (ADR 10). An ensure that fails, times out or prints anything else logs one line with its stderr (both credentials redacted), sends nothing and exits 0. The script unsets `SOCK_TOKEN` and `CLAUDE_PLUGIN_OPTION_SOCK_TOKEN` once it has read them, so no child but the one sock call sees a credential. sock-mcp makes the same swap for its own process.
2b. The Codex plugin route (`PLUGIN_ROOT` set and a `turn_id` in the hook input, a field only Codex sends, documented as a Codex-specific extension at [Codex hooks](https://learn.chatgpt.com/docs/hooks); not `CLAUDE_PLUGIN_ROOT`, which the same page says Codex also sets for plugin hooks "for compatibility", so it cannot tell the routes apart, nor whether the option is empty) always sends with `sock send --as-puppet --project "$PLUGIN_ROOT"` (sock-cli v0.2.5 or later). The CLI resolves the credential exactly as the plugin's sock-mcp does, which runs in `PLUGIN_ROOT`: `SOCK_TOKEN`, else the config file's `machine_key` through ensure for that directory, else its `puppet_token`, never the login token (sock-client `ResolvePuppet`), so the hook and the server send as one puppet (integrations-zpe). `SOCK_TOKEN`, `SOCK_URL`, `SOCK_ACCESS_GATE` and `CLAUDE_PROJECT_DIR` are unset for that call: the plugin's sock-mcp never sees the first three, so an exported `SOCK_TOKEN` would make `ResolvePuppet` pick a different puppet and the config file must pick the server for both, and the CLI lets `CLAUDE_PROJECT_DIR` override `--project`. A refusal (no puppet credential) logs one line through rule 6 and sends nothing. The Claude Code plugin and manual routes keep rules 2 and 2a.
3. Only the ask and permission prompts send (rule 8d). `finished a turn` (the `notify_on_stop` option and `SOCK_NOTIFY_ON_STOP`, removed 2026-10-14 with the option) and the v1 fixed phrase (no mode) send nothing.
4. Text is `<name>: <body>`, where `<name>` is the basename of `CLAUDE_PROJECT_DIR`, else `PWD`. Under `LC_ALL=C` the name keeps only `[A-Za-z0-9._ -]`, is cut to 100 characters, and becomes `project` when nothing remains.
5. Run `sock send` with the text on stdin, never in argv, so another user's `ps` cannot read it, as a child with a watchdog that sends TERM after `SOCK_HOOK_TIMEOUT` seconds, default 10, and KILL two seconds later; a value that is not a positive integer falls back to 10. Async hooks are not timed out by the host, so the script bounds itself. The watchdog is reaped without a job notice on stderr.
6. Any failure, including `sock` missing from `PATH`, appends one line to `${XDG_STATE_HOME:-$HOME/.local/state}/sock-integrations/hook.log` (mode 600, truncated above 100 KB). A failed send logs `sock send exit <code>:` and the child's stderr, with the token and every secret shape of rule 1a redacted from the whole captured stderr first and the result then cut to 300 bytes, so a token straddling the cut cannot leak a prefix. Every control character, C1 included (raw 0x80-0x9F and UTF-8 C2 80-9F, with any byte outside a well-formed UTF-8 sequence), is stripped from the line, so tool output cannot drive a terminal that reads the log. The line never contains the token.
7. Exit 0 always.
8. Only an interactive session messages the owner, and at most once an hour per project. The owner got dozens of sock messages from agents overnight (2026-10-14) and says people would ignore or uninstall a tool that does that. Only the trimmed ask and permission prompts send, and both go through one gate, after the per-turn dedupe of rule 1a:
   - 8a. Classify the session; only a positive signal is interactive, and anything unrecognized is quiet (fail closed):
     - `SOCK_HEADLESS` set: background. `runner/sock-runner` sets it for the agent it resumes, because a Codex session resumed by `codex exec resume` keeps the `source` it was created with, which can be the TUI's (live probe: resume appends no new `session_meta`).
     - No `session_id` in the input (no `jq`, input not JSON): unknown.
     - `agent_id` in the input: background, except a permission prompt (`--permission`) in an attended Claude Code session (below), which holds up the session the owner is in and spends the same hourly budget; a subagent's ask stays quiet. Teammates and `--bg` sessions have `CLAUDE_CODE_SESSION_ATTENDED=0`, so their prompts stay quiet. Claude Code sets it when the hook fires inside a subagent or in-process teammate ([hooks, common input fields](https://code.claude.com/docs/en/hooks)); Codex sends it on subagent events ([Codex hooks](https://learn.chatgpt.com/docs/hooks)).
     - Claude Code: `CLAUDE_CODE_SESSION_ID` equal to the input's `session_id` (documented to match it for hook commands, [env vars](https://code.claude.com/docs/en/env-vars)), then `CLAUDE_CODE_SESSION_ATTENDED`: `1` interactive, `0` background, anything else unknown. The match binds the variable to this session, so one inherited from an outer Claude Code session (Codex started from its Bash tool) is not read as this session's. `CLAUDE_CODE_SESSION_ATTENDED` is undocumented: Claude Code 2.1.299 sets it in every hook's environment from its own attended check, `0` for a `bg`, `daemon` or `daemon-worker` session kind and for a teammate, `1` for the interactive TUI and for a top-level human host entrypoint (`claude-vscode`, `claude-desktop`, `remote_*` and the like), `0` otherwise, so `-p` (`sdk-cli`) and the Agent SDK (`sdk-ts`, `sdk-py`) are `0`. Read from the 2.1.299 bundle and checked live: a `claude -p` hook got `CLAUDE_CODE_SESSION_ATTENDED=0` and `CLAUDE_CODE_ENTRYPOINT=sdk-cli`, while the Bash tool of the interactive session that built this rule carried `1` and `cli` (the bundle builds the Bash and hook environments with one function; an interactive hook was not probed). A Claude Code without the variable is unknown, so quiet. `CLAUDE_CODE_ENTRYPOINT` is not read: also undocumented as a variable, and attended already folds it in. The input JSON has no headless field: a `-p` hook input matches an interactive one field for field (`permission_mode` is `default` in both), and `Notification` did not fire at all in the `-p` probe.
     - Codex: the first line of `transcript_path` (read only when it is a regular file, its first 4 MiB) is the `session_meta` record; when its `payload.id` is the input's `session_id`, `payload.source` `cli` (the TUI) or `vscode` (the Codex app and IDE) is interactive, `exec` and a `subagent` object are background, anything else unknown. The Codex hooks docs name no field or variable that marks `codex exec` ([Codex hooks](https://learn.chatgpt.com/docs/hooks); `developers.openai.com/codex/hooks` redirects there); the hook input of a live `codex exec` (0.162.1, throwaway `CODEX_HOME`) carried `session_id`, `turn_id`, `transcript_path`, `cwd`, `hook_event_name`, `model` and `permission_mode` only, and its transcript's `session_meta` had `source: "exec"`, `originator: "codex_exec"`; local TUI sessions have `source: "cli"`, `originator: "codex-tui"`, the app `vscode`. `approval_policy` is not a signal: an `exec` session can run `on-request`.
   - 8b. An interactive session sends at most once an hour per project. The project is the name of rule 4; its last send is epoch seconds in `throttle/<project>.at` in the state directory (mode 600 in a 700 directory, written to a temp file and renamed), checked and recorded under a `mkdir` lock (`<project>.at.lock`) so two hooks firing together cannot both send. A lock older than a minute (a killed hook's) is removed under a second guard, `<project>.at.lock.break`, that rechecks it, itself removed when older than a minute; the hook that finds a stale lock stays quiet that run, so two hooks that found it together cannot both take it and send. Permission prompts count against the same hour. A send that fails gives the hour back. A record in the future does not hold sends back.
   - 8c. A reply to a message the owner sent in the sock chat is always allowed, from any session, never throttled or suppressed. Replies are the model's `sock_send` through sock-mcp, and the hooks never touch them: no hook runs on `PreToolUse` or `PostToolUse`, every hook is `async`, and nothing counts a `sock_send` against the hour (a test pins the hook events of all three `hooks.json` files).
   - 8d. Everything else sends nothing (`finished a turn` and the v1 phrase are gone), with no digest of what was held back. Each suppression logs one line through rule 6 with a fixed outcome, `quiet: background`, `quiet: unknown session` or `quiet: throttled`, never the text.

## Headless inbound: sock-runner

Codex and a `claude -p` agent have no channel: nothing pushes a message into a session that is idle. The inbound path is the CLI's `sock listen --exec`, which streams the puppet's deliveries and calls a command once per message. `runner/sock-runner` is that command: it resumes the agent's session headlessly with the owner's message as the prompt. It adds no server surface and no state of its own besides a lock, a log, a ledger of finished ids and, for `claude` without `SOCK_RUNNER_SESSION`, the id of the session it made.

Rejected: a `Stop` hook that fetches pending messages. It fires only at the end of a turn, so an idle session never fetches, and it would consume the puppet's deliveries beside the channel (rule 2).

### Invocation

```sh
SOCK_TOKEN=sock_pt_...  SOCK_URL=...                      # the runner's own puppet, see Rules
SOCK_RUNNER_AGENT=claude                                  # claude | codex, required
SOCK_RUNNER_SESSION=<session id>                          # optional for claude, required for codex: a session nobody has open
SOCK_RUNNER_WORKDIR=<dir>                                 # required, an existing directory
SOCK_RUNNER_PERMISSION=<mode>                             # required, no default
sock listen --exec /path/to/runner/sock-runner
```

Optional: `SOCK_RUNNER_TIMEOUT` (seconds an agent run may take, default 900; not a positive integer falls back to 900), `SOCK_RUNNER_STATE` (directory of the lock and log, a relative one taken from where the runner starts, default `${XDG_STATE_HOME:-$HOME/.local/state}/sock-integrations`).

`SOCK_RUNNER_PERMISSION` is the agent's headless permission posture, passed through and never derived from a message, and it is an allowlist: exactly the agent's own modes, anything else exits 2 before a message is read. For `claude`: `acceptEdits`, `default`, `dontAsk`, `manual`, and `auto` and `bypassPermissions`, which also need `SOCK_RUNNER_ALLOW_BYPASS=1` (auto mode approves beyond acceptEdits). The list is the CLI's own `--permission-mode` choices plus `default`, which it accepts. For `codex` the `--sandbox` value: `read-only`, `workspace-write`, and `danger-full-access`, which also needs `SOCK_RUNNER_ALLOW_BYPASS=1`. `plan` is refused for `claude` (exit 2): live-checked with claude 2.1.296, plan mode blocks non-read-only tools such as `sock_send` regardless of `--allowedTools`, the model then says it could not send, claude exits 0 and the runner would log `ran`. Documented defaults: `default` and `read-only`.

There is no prompt to answer in a headless run, and an MCP tool that is not pre-approved is denied. So for `claude` the runner always passes `--allowedTools` with the three sock tools the plugin serves, `--disallowedTools` for the other two (`sock_fetch` and `sock_ack` consume the deliveries `sock listen` owns, so rule 2 holds even under `bypassPermissions`), and `--permission-prompts none`: without them `sock_send` is refused in every mode but `bypassPermissions` and the owner never hears back. The names follow Claude Code's plugin tool convention, `mcp__plugin_<plugin>_<server>__<tool>` with any character outside `A-Za-z0-9_-` replaced by `_` ([MCP docs, "Plugin MCP tool names"](https://code.claude.com/docs/en/mcp)): plugin `sock`, server `sock`, so `mcp__plugin_sock_sock__sock_whoami`, `..._sock_list_conversations` and `..._sock_send`. A test derives them from `plugin.json` and `.mcp.json` and fails if either name changes. For `codex`, `codex/config.toml` sets `enabled_tools` to those three tools and `default_tools_approval_mode = "approve"` for the sock server ([Codex MCP config](https://learn.chatgpt.com/docs/extend/mcp)); both keys apply to every Codex session that merges the file, interactive ones included, which `codex/install.md` says. Not yet checked against a live `codex exec` (tracked as a bead).

### Interface with sock listen

`sock listen --exec` (sock-cli `internal/cli/listen.go`, `handle`) runs the command once per message, with:

- stdin: the message as `protojson` of `sock.v1.Message`, one object: `id`, `conversationId`, `seq` (int64, so a JSON string), `senderId`, `sentAt` (RFC 3339), `text`, `evidenceTag` (base64). protojson randomizes whitespace between tokens, so the runner never matches on exact bytes.
- env: `SOCK_MESSAGE_ID`, `SOCK_CONVERSATION_ID`, `SOCK_SENDER_ID`. Ids only, never text.
- exit status: 0 acknowledges the message; non-zero leaves it pending, `listen` retries up to 5 times with backoff and then holds it for the next connection. Delivery is at least once, so a run may repeat after a crash between the agent finishing and the ack.

### Behavior

1. Validate configuration: `jq` and `sock` on `PATH` (jq decodes the protojson text exactly, escapes and surrogate pairs included), agent, workdir and permission present, a session for `codex`, a `SOCK_RUNNER_SESSION` that is set matching `[A-Za-z0-9._-]{1,128}`, workdir an existing directory, `claude` or `codex` on `PATH`. A bad configuration exits 2 and acknowledges nothing; the message stays pending and the log says why.
2. The owner gate. The sender must be the puppet's owner: `SOCK_SENDER_ID` and the `senderId` in the stdin JSON must be the same UUID, settled before any network call, and equal `account.puppet.ownerId` from `sock whoami --json`, run with the same token. The owner id is cached for 60 seconds in the state directory, keyed by a hash of the token, so a non-owner in a shared conversation costs no call per message. A token whoami does not show as a puppet (a human session) is a configuration error: exit 2, nothing acknowledged, stderr and the log say why. Acknowledging would consume that human account's own deliveries and lose them, and `sock listen` does not wedge on the failure: it retries the message five times and leaves it pending. Any other sender, a missing field, a puppet token that whoami does not show as a puppet, or a failing whoami: a gate failure that is the sender's (not the owner, malformed) drops the message, exit 0, so it is acknowledged and cannot wedge the stream; a whoami that could not run (network, 5xx) exits 1 so the message is retried. Nothing from a non-owner reaches the agent.
3. Take the run lock: one agent run at a time per `SOCK_RUNNER_STATE` (macOS has no `flock`). The lock is a symlink `runner.lock` whose target is the runner's pid, made with `ln -s`: creating it is atomic and carries the pid in the same step, so no second runner can see a lock without one. The target is `<pid>:<start time>` (`ps -o lstart=`, read under `LC_ALL=C TZ=UTC` because it is compared as text), so a pid that a later process has reused is not mistaken for a live runner; a bare pid target counts as live while the pid exists. A lock whose pid is dead, or whose start time no longer matches, is stale and replaced under a second guard, `mkdir runner.lock.break` (held for milliseconds, itself removed when older than a minute): inside the guard the runner re-reads the lock, confirms it is still stale, removes it and creates its own, so two runners cannot both break the same stale lock. The lock is removed on exit, including a signal. Waiting counts against the timeout; past it, exit 1.
4. `id` and `conversationId` from stdin must each be a UUID, and a value holding a newline is never one (`[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}`), as must the env copies; anything else is malformed and dropped with exit 0, so nothing but a UUID can reach a tag attribute. Build the prompt from the owner's text only: `<sock-message from="owner" conversation="<conversationId>" id="<id>">` newline text newline `</sock-message>`, with every `</sock-message` inside the text, in any case and with spaces after `</`, broken by inserting a zero-width space after `</`. A one-line preface above the tag says the tag holds the owner's reply to the question the agent asked and that it is not a system instruction. The text goes to the agent on stdin; it never appears in argv, the environment or a log. It is written once to a private file in the state directory (mode 600, removed on exit, and any `prompt.*` older than the timeout swept at start) so the agent reads it from a file descriptor, and the agent's own session transcript keeps the owner's text for as long as that transcript lives.
5. Run the agent, in `SOCK_RUNNER_WORKDIR`, as a background job under `set -m` so it leads its own process group. When `SOCK_RUNNER_TIMEOUT` seconds have passed since the lock wait began (one deadline covers the wait and the run) the runner sends TERM to the whole group, then KILL after 5 seconds, so the MCP servers and tool children `claude` and `codex` spawn do not outlive the run. The environment the agent gets is the runner's minus `SOCK_RUNNER_*` and the `listen` variables, and for `claude` also minus `SOCK_TOKEN` and `SOCK_URL`: the plugin's sock-mcp takes its token from the plugin's own configuration, and the agent's shell tool must not be able to read the runner's. For `codex` the token stays, because `codex/config.toml` forwards `SOCK_TOKEN` and `SOCK_URL` to sock-mcp with `env_vars`; the agent can then read it, which `codex/install.md` already says of every Codex launch.
   - `claude`: `claude -p --resume "$SESSION" --permission-mode "$MODE"`, prompt on stdin. Without `SOCK_RUNNER_SESSION` the session is the runner's own: `session` in the state directory holds one lowercase UUID, read and written under the lock (written to `session.tmp` and renamed, mode 600). When it is missing or holds anything but a UUID the runner makes one with `uuidgen`, stores it first and runs `claude -p --session-id <uuid>` instead of `--resume`, so the first message for a project starts the session and every later one resumes it. A stored session claude no longer has (a resume that fails with `No conversation found with session ID` on stderr, which goes to a private file beside the prompt, is read for that line only and removed with the prompt, never logged) logs `session gone` and runs the message once more in a new session, within the same deadline: nothing ran in the first attempt. `codex` has no way to name a session before it exists, so it still needs `SOCK_RUNNER_SESSION`.
   - `codex`: `codex exec --sandbox "$MODE" resume "$SESSION" -`, prompt on stdin (`--sandbox` is an option of `exec`; `exec resume` has none).
   The agent replies with `sock_send` through the plugin's sock-mcp (outbound only, rule 2); the runner sends nothing. Both agents run with `SOCK_HEADLESS=1`, so their `notify.sh` hooks stay quiet (notify.sh rule 8a).
6. Redelivery: `listen` is at-least-once, so before running, the runner checks `done.ids` in the state directory, the last 200 message ids that finished with agent exit 0, before it waits for the lock (so a repeat does not queue behind a running turn) and again once the lock is its own, and acknowledges a repeat without running it (`duplicate`). The id is added under the lock after a successful run; a failed or timed-out run is not remembered, so its retry runs. Exit 0 when the agent exits 0. The watchdog writes its timeout mark only while the agent's group is still alive, so an agent that finished just before the deadline is not a timeout, and a timeout beats exit status: an agent that exits 0 on the watchdog's TERM did not finish. Any other agent exit, or a timeout: exit 1 so the message is retried. A prompt that crashes the agent every time is retried five times and then held pending, which is why the lock and timeout bound the damage.
7. Log one line per message to `runner.log` in the state directory (mode 600, truncated above 100 KB): time, message id, outcome (`ran`, `session gone`, `session id failed`, `session not writable`, `dropped: sender <uuid>`, `dropped: malformed`, `whoami failed`, `not a puppet token`, `duplicate`, `locked`, `prompt file failed`, `agent exit <n>`, `timeout`). Never the text, the token, or the agent's output, its stderr included. A failed log write never changes the exit status, as in `notify.sh`.

### Rules that follow

- The `listen` process is the single consumer of the runner's puppet: nothing calls `sock_fetch` or `sock_ack` for it, and no session that accepted the development channel runs as it (rule 2). Under the runner service that puppet is the project's (Runner service).
- Use one `SOCK_RUNNER_STATE` per runner: two runners sharing the default directory share one lock, one ledger and one log (and the directory `notify.sh` logs to).
- `sock listen --exec` runs its command through `/bin/sh -c`, so the runner's path must contain no spaces or shell metacharacters.
- A session the runner resumes must be one no one has open: a resume while the same session is open in an interactive client interleaves two writers on one transcript. Leave `SOCK_RUNNER_SESSION` unset under `claude` and the runner makes and keeps its own.
- Run `sock listen` and the agent as the same user, in the workdir's project. The token comes from the environment (`SOCK_TOKEN`), as everywhere in this repo.
- Message text is untrusted data even from the owner: the permission mode is the control, and the default is the most restrictive.
- At-least-once: the agent may see a message twice. The prompt carries the message id so the session can recognise a repeat.

### Runner service

`runner/sock-runner-service install <project dir>` keeps `sock listen --as-puppet --project <dir> --exec <repo>/runner/sock-runner` running for one project as a user service: a launchd agent (`~/Library/LaunchAgents/ai.aeryx.sock-runner.<id>.plist`, `RunAtLoad`, `KeepAlive`, `ThrottleInterval` 10) on macOS, a systemd `--user` unit (`sock-runner-<id>.service`, `Restart=always`, `RestartSec=5`, `WantedBy=default.target`) on Linux. `<id>` is the first 16 hex of the SHA-256 of the project's physical path, so a project has one unit and reinstalling replaces it (launchd: `bootout` then `bootstrap` in `gui/<uid>`; systemd: `daemon-reload`, `enable --now`, `restart`). `uninstall <project dir>` stops and removes it.

- No credential in the unit. `sock listen --as-puppet` (sock-cli, requested from sock-ops) resolves the project's puppet as `sock send --as-puppet` and the plugin's sock-mcp do (sock-client `ResolvePuppet`: `SOCK_TOKEN`, else the config file's `machine_key` through `puppets ensure` for the project, else `puppet_token`), and passes the resolved token and URL to the `--exec` child as `SOCK_TOKEN` and `SOCK_URL`. So the runner listens as the same puppet the agent's sock-mcp replies as, and the conversation ids it hands the agent are that puppet's. The installer refuses (exit 2) a `sock` whose `listen --help` lacks `--as-puppet`.
- The unit carries the runner's settings: `SOCK_RUNNER_AGENT` (default `claude`), `SOCK_RUNNER_PERMISSION` (default `default`), `SOCK_RUNNER_WORKDIR` (the project), `SOCK_RUNNER_STATE` (`${XDG_STATE_HOME:-~/.local/state}/sock-integrations/runner/<id>`, one per project, so runners never share a lock or ledger), the installing shell's `PATH` (the agent, `jq` and `sock` must resolve under launchd), and `SOCK_RUNNER_SESSION`, `SOCK_RUNNER_TIMEOUT` and `SOCK_RUNNER_ALLOW_BYPASS` when set. The installer runs the runner's own configuration check (`runner_config` in `lib.sh`) first, so a unit never starts with settings the runner would refuse at every message. `listen`'s stderr goes to `listen.log` in the state directory.
- Values go into a plist or unit file unquoted and through `sh -c`, so paths and settings are limited to `A-Za-z0-9._/@+-` (and `:` in `PATH`); anything else exits 2.
- One consumer per project puppet: the service, or an interactive Claude Code session that accepted the development channel for that project, never both. Both would consume the same deliveries (rule 2). With sock-mcp v0.3.3 a session without an accepted channel does not consume, so ordinary interactive sessions in the project are fine beside the service.
- Linux needs `loginctl enable-linger $USER` for the unit to run without a login session.

### Managed Agents bridge: sock-bridge

A Claude Managed Agents session runs on Anthropic's side and is steered by events: the owner's reply goes in as a `user.message`, and the agent's answer comes back as `agent.message` events. `runner/sock-bridge` is the `sock listen --exec` command that carries one owner reply into one session and the agent's answer back to the owner. Conformist downstream of two upstreams, `sock listen --exec` and Anthropic's Managed Agents API (beta header `managed-agents-2026-04-01`; [events and streaming](https://platform.claude.com/docs/en/managed-agents/events-and-streaming)); it adds no server surface and no domain model, and it is the anti-corruption layer between the two vocabularies: a sock message in, session events out, never a session event vocabulary inside sock.

Not a daemon of its own. A daemon wrapping `sock listen` would duplicate what `listen --exec` already does (reconnect, backoff, at-least-once, ordering, ack on exit 0) and keep a second copy of stream state. A command run once per message, like `sock-runner`, reuses all of it: the turn is synchronous inside the command, and the ack is the exit code. The cost is that one long agent turn holds the stream; the timeout bounds it, and Managed Agents queues events anyway. Keeping `sock listen` itself running is the OS service manager's job, not a daemon of this repo's: see "Runner service" (the earlier "no service" line is superseded there).

### Invocation

```sh
export SOCK_TOKEN=sock_pt_...             # the bridge's own puppet, no other consumer
export ANTHROPIC_API_KEY=...              # a key that may use this session
export SOCK_BRIDGE_SESSION=sesn_...       # an existing session; or, instead:
# export SOCK_BRIDGE_AGENT=agent_... SOCK_BRIDGE_ENVIRONMENT=env_...   # a session per conversation
sock listen --exec /path/to/runner/sock-bridge
```

Optional: `SOCK_BRIDGE_TIMEOUT` (seconds one turn may take, default 900; not a positive integer falls back), `SOCK_BRIDGE_API` (default `https://api.anthropic.com`; the key goes there, so it must be an https URL or http to `localhost` or `127.0.0.1`, else exit 2), `SOCK_BRIDGE_MAX_STREAM` (bytes the event stream may hold, default 32 MiB), `SOCK_BRIDGE_STATE` (default `${XDG_STATE_HOME:-$HOME/.local/state}/sock-integrations-bridge`; one per bridge). `SOCK_BRIDGE_API` (default `https://api.anthropic.com`) exists for tests and is not for production use. The bridge does not set the agent's tools or choose its permission policy: those live in the agent and environment definitions on Anthropic's side, and their owner chooses them. With `SOCK_BRIDGE_AGENT` instead of `SOCK_BRIDGE_SESSION` it creates a session per conversation (below).

### Interface

stdin, env and exit codes are `sock-runner`'s (the `sock listen --exec` contract above): exit 0 acknowledges, 1 retries, 2 is a configuration error and runs nothing. The same gate and the same input hygiene apply, shared in one library file `runner/lib.sh` that both commands source: UUID-checked ids, env and stdin senders equal, the sender equal to `account.puppet.ownerId` (cached 60 seconds), a non-owner or malformed message acknowledged and dropped, the state-directory lock so one turn runs at a time, the log of fixed strings and ids only.

### Behavior

1. Configuration: `SOCK_BRIDGE_SESSION` matching `[A-Za-z0-9_][A-Za-z0-9_-]{0,127}` as a whole value (one with a newline never matches), or the session-per-conversation settings below, `ANTHROPIC_API_KEY` present, `curl`, `jq` and `sock` on `PATH`. Anything else exits 2.
2. The gate and the lock as in `sock-runner`.
3. Redelivery state: `done.ids` (the last 200 ids whose answer was posted: a repeat is acknowledged without work, `duplicate`) and `sent.ids` (ids whose `user.message` was or may have been posted). The id goes into `sent.ids` before the POST, so a run killed or failed between the post and the record cannot send it twice. A message in `sent.ids` is first looked up in the session's history (step 7); only when the history, read in full, does not hold it does the bridge send.
4. Open the event stream first (`GET /v1/sessions/$SESSION/events/stream?beta=true`, `accept: text/event-stream`); a stream shows only events after it opens, so it is open before the send. Then send the owner's reply: `POST /v1/sessions/$SESSION/events?beta=true` with `{"events":[{"type":"user.message","content":[{"type":"text","text":"<prompt>"}]}]}`. The prompt is the runner's: a one-line preface and `<sock-message from="owner" conversation=... id=...>` around the text, closing tags broken, so the id is in the session's history and a redelivery can find it.
5. Follow the stream until the turn ends. The turn starts at this run's own `user.message`, the one whose second line is this message's tag: the stream opened before the send, so events before it (a turn still running, its answer and its idle) are another turn's and ignored. The docs do not say the stream echoes a `user.message`, so the bridge works either way: a `session.status_idle`, `session.error`, `session.status_terminated` or `session.deleted` that arrives before this run's own `user.message` means the stream cannot place the turn. Nothing from it is posted; the bridge closes the stream, logs `stream unanchored` and finishes from history (step 7, the same reducer), polling every 2 seconds until the turn is done or the deadline. Only whole lines are events: the stream file is read by byte offset and a trailing line without its newline waits for the rest. Keep the text blocks of `agent.message` events (buffered events, one per model request) in order, once per event id (an event whose id is not a string of 1 to 256 characters without a control character is refused, one with no id kept), and ignore everything else, thinking and tool events included: tool inputs and outputs can hold secrets and never reach sock. The file is bounded (`SOCK_BRIDGE_MAX_STREAM`; past it the bridge exits 1, `stream too large`) and each poll reads only the new bytes in one `jq` pass, so a flood costs linear time and the deadline is checked every poll. The turn ends at `session.status_idle` with `stop_reason.type`:
   - `end_turn`: post the collected text to the owner (an empty or whitespace-only answer posts `the agent finished without a reply`), exit 0.
   - `requires_action`: tool calls wait for an answer. Each call evaluated `ask` gets a code the owner answers with `approve <code>` or `deny <code> <reason>` (below). A call the bridge cannot answer from sock (a custom tool, one it did not see) posts the fixed text `the agent is waiting for approval of a tool call` (no tool name, no input) and the owner answers in the Managed Agents console. Exit 0.
   - `budget_reached`: post `the agent's budget is used up`, exit 0.
   - `session.error`, and `session.status_terminated` or `session.deleted` (a session ended by an unrecoverable error or deleted never goes idle; platform.claude.com/docs/en/managed-agents/reference, "Session events"): post `the agent hit an error`, exit 0. A stream that ends without idle exits 1 (`stream dropped`), so the retry finishes from history.
6. Posting: `sock send` with the text on stdin (the puppet's `NotifyOwner`; argv is visible in `ps`), control characters other than newline and tab removed, C1 and CR among them, and the bidi controls (U+202A to U+202E, U+2066 to U+2069) and U+2028 and U+2029 (an agent's answer can hold terminal escapes, or text that reorders what the owner's client shows), at most 60000 bytes per message, split on blank lines, then lines, then bytes, never inside a UTF-8 character; at most 5 parts, the last saying the rest was cut. After each part the bridge writes `<id> <n>` to `posted.part`, so a retry of a message whose part n failed posts only the remaining parts. Record `replied` (`done.ids`) after the last part, then exit 0. `posted.part` makes a redelivery skip every part already posted, so a crash between the last part and `replied` posts nothing again.
7. Catch-up from history (an id in `sent.ids`): list the session's events (`GET /v1/sessions/$SESSION/events?beta=true`, following `next_page` through `page=`; events come oldest first), find the last `user.message` whose text's second line, after the preface, is exactly this message's opening tag (a tag quoted inside a message's text is on a later line and does not count), read the events after it exactly as step 5 reads the stream (one jq reducer serves both, so the two cannot disagree on the text, the ids or the outcome; an idle without a stop reason is `end_turn` on both), and continue at step 5's outcomes. The message is there but the agent has not finished: poll the history every 2 seconds until it has, or exit 1 at the deadline. The message is not there: the post never landed, so the bridge sends it (steps 4 and 5).
8. HTTP politeness: `User-Agent: sock-bridge`, a connect timeout and an overall turn timeout, `Retry-After` honored (seconds or HTTP date, any digit string, never past the time left) with exponential backoff otherwise. 429 is retried a few times for any request, and 5xx and network failures too for a GET; a POST that failed any other way may have landed and is never repeated (exit 1, and the redelivery asks the history). 401, 403 and 404 exit 2 (the key or session is wrong; retrying cannot help), except that a 404 on a session the bridge created exits 1, so the retry checks it again and replaces it. Every curl call takes `-q` first, so no curlrc is read, `--proto` and `--proto-redir` limited to the API's scheme, and `--max-redirs 0`. The key goes to curl on a private config file (`--config`), never in argv, the environment of any child or the log. The key's charset is checked (`A-Za-z0-9_.-`) so it cannot break out of a config line.
9. Log to `bridge.log` (mode 600, truncated above 100 KB) one line per message, plus one per session step: time, id, outcome. The outcomes: `ran`, `waiting for approval`, `budget`, `agent error (<stop reason>)` (the API's stop reason when it is `[a-z_]{1,40}`, else `unknown`), `dropped: sender <uuid>`, `dropped: malformed`, `not a puppet token`, `whoami failed`, `duplicate`, `locked`, `prompt file failed`, `ledger not writable`, `stream dropped`, `stream too large`, `send failed`, `http <status>` (`000` for a network failure), `http bad history`, `history too long`, `timeout`; the stream step `stream unanchored` (an end seen before this run's own `user.message`, finished from history); and the session steps `session created`, `session adopted`, `session gone`, `session id invalid`, `session does not fit`, `session drifted`, `create halted`, `halt not writable`, `session config changed`, `sessions not readable`, `sessions not writable`; and the confirmation outcomes `approval requested`, `approval recorded`, `approval pending`, `approval not pending`, `approval refused`, `confirm not writable`, `no code`. Never the text, the answer, the key or the token.

### Rules that follow

- The bridge's puppet is its own and its one consumer is `sock listen`. Nothing calls `sock_fetch` or `sock_ack` for it.
- Temp files are named `<prefix>.<pid>` in the state directory and removed on exit, a TERM's included: every sleep and request runs as a job the command waits on, so the trap acts at once; the next run removes those of pids that no longer exist, and any older than a run can last whatever its pid (a pid can be reused, and `curl.*` holds the key), so a SIGKILL cannot leave the curl config and its key behind for long (an orphaned stream curl ends at its `--max-time`, the turn deadline). A state directory that is unwritable or cannot be made this user's alone (owner, mode 700), or a relative one when the start directory is gone, exits 2 before any wait, for both commands.
- One session per bridge (`SOCK_BRIDGE_SESSION`) or per conversation (`SOCK_BRIDGE_AGENT`), and the session is not driven by anything else at the same moment: two writers interleave turns, and the bridge cannot tell whose answer a `session.status_idle` ends.
- The owner's reply is data to the agent, in a tag, like everywhere in this repo. What the agent may do is the session's own configuration.
- The agent's answer goes only to the owner, over the bridge's puppet, as ordinary messages.

### Tests

Under `test/`, with a fake Managed Agents server (Go `httptest`, speaking the stream and events endpoints) and stub `sock` and `curl` where the harness needs them: the stream is open before the send; the request has the headers `x-api-key`, `anthropic-version` and `anthropic-beta: managed-agents-2026-04-01` and the `user.message` body; text blocks of `agent.message` are posted once at `end_turn` and thinking and tool events never are; `requires_action`, `budget_reached` and `session.error` post only their fixed texts; a dropped stream exits 1 and the retry finishes from history without a second `user.message`; a `replied` id is a duplicate; a long answer is split and bounded; 429 with `Retry-After` is honored and 5xx retried then exit 1; 401, 403 and 404 exit 2; the key is in no argv, child environment, log or file other than the private curl config, which is removed; the owner gate, the lock and the input hygiene hold as in the runner's tests (shared cases run against both commands).

Security review before merge, as the review gate below: sender spoofing and the gate, injection through the text into the tag or the API body, the key's exposure (argv, environment, logs, files, `curl` config), the lock and ledger races, and a hostile or malformed event stream (very large events, a flood of `agent.message`, events that never reach idle).

### Session per conversation (integrations-kzk)

Built. The bridge creates a Managed Agents session the first time a conversation reaches it, from an agent and an environment in its configuration, instead of requiring `SOCK_BRIDGE_SESSION`. One session per sock conversation, not one per bridge: a conversation is the unit of context the owner sees, and the rule that one writer drives a session then holds by construction. Sources: [sessions](https://platform.claude.com/docs/en/managed-agents/sessions), [session operations](https://platform.claude.com/docs/en/managed-agents/session-operations), [create](https://platform.claude.com/docs/en/api/beta/sessions/create) and [list](https://platform.claude.com/docs/en/api/beta/sessions/list) in the API reference, [rate limits](https://platform.claude.com/docs/en/managed-agents/reference#rate-limits).

Configuration, checked before the message is read, each value matched whole (a newline never matches), any failure exit 2 with no request:

- `SOCK_BRIDGE_AGENT`: the agent id, `agent_[A-Za-z0-9]{1,120}`. Setting it selects this mode. Set together with `SOCK_BRIDGE_SESSION`: exit 2, the two modes do not mix.
- `SOCK_BRIDGE_ENVIRONMENT`: required with the agent, `env_[A-Za-z0-9]{1,120}`.
- `SOCK_BRIDGE_AGENT_VERSION`: optional, a positive integer of at most 9 digits (the API's version is an int32 of at least 1); set, the session pins `{"type":"agent","id":...,"version":N}`, unset the agent goes as its id string and the session takes the latest version.
- `SOCK_BRIDGE_BUDGET`: optional, whole US cents as digits without a leading zero, at most 9 digits, sent as `{"type":"limit","max_list_cost":{"amount":"<cents>","currency":"USD"}}` (the amount is a string; `USD` is the only currency). A budget can only be attached at creation, so a bridge that creates sessions on its own is where the cap belongs; unset means no cap, as the API's default.
- `SOCK_BRIDGE_ENVIRONMENT`, `SOCK_BRIDGE_AGENT_VERSION` or `SOCK_BRIDGE_BUDGET` without `SOCK_BRIDGE_AGENT`: exit 2, they would silently do nothing.

The tools, MCP servers, vaults and permission policies stay the agent's and the environment's, chosen by their owner on Anthropic's side, as now.

API calls, all with the existing headers (`x-api-key` from the private curl config, `anthropic-version: 2023-06-01`, `anthropic-beta: managed-agents-2026-04-01`, `User-Agent: sock-bridge`) and the existing retry classes (a GET retries 429, 5xx and network failures; a POST retries only 429; 401 and 403 exit 2):

| Call | Method and path | Idempotency | On failure |
|---|---|---|---|
| Find | `GET /v1/sessions?beta=true&agent_id=$AGENT&order=desc&limit=100`, following `next_page` through `page=`, at most 10 pages | Read | GET class |
| Create | `POST /v1/sessions?beta=true` with `agent`, `environment_id`, `title` `sock <first 8 of conversationId>`, `metadata` `{"bridge_conversation": <conversationId>, "bridge_puppet": <account.id>}`, `budget` when set; no `initial_events` | None: the API takes no idempotency key, so a create that may have landed (5xx, a dropped connection) is never repeated (exit 1) and the retry finds it | 400 or 404: exit 2 (the agent or environment is wrong or archived) |
| Check | `GET /v1/sessions/$SESSION?beta=true`, once per turn of a mapped session | Read | GET class; 404 means gone |

The created session starts `idle` and its sandbox provisions at once; the existing turn (stream, then `user.message`) follows unchanged, and a created, adopted or mapped session's turn is read by the same reducer as any other, from this run's own `user.message` on, with the same history fallback. Find, Create and Check go through the same request helper, so they take the same curl flags and retry classes. No `initial_events`: the stream must be open before the first event, and it cannot open before the session exists. Metadata is at most 16 pairs, keys up to 64 characters and values up to 512; the two pairs here are a UUID each.

State: `sessions` in the state directory, one line `<conversationId> <session id> <config hash>` per conversation (the hash is the breaker's, below, of the configuration the bridge created or adopted the session under; a two-field line from before the hash was recorded has an unknown hash), mode 600, read and rewritten only under the existing run lock (`bridge.lock`), written to `sessions.tmp` and renamed, so a crash leaves the old file or the new one. The lock already serializes every turn of a bridge, so the map needs no lock of its own. A session id, from a create response or a Find, must match `[A-Za-z0-9_][A-Za-z0-9_-]{0,127}` as a whole value, as `SOCK_BRIDGE_SESSION` does: a create answer that does not is never recorded (`session id invalid`) and trips the create breaker below: Find would never adopt that session, and `sock listen` retries exit 2 as it does exit 1, so without the breaker every delivery of every later message would create another. A listed session that does not match is never adopted. A `sessions` file the bridge cannot read fails closed before any request (`sessions not readable`, exit 1), and the rewrite takes the other conversations' lines from a read whose status it checks, so a failed read can never rename a map of one line over the whole map.

Create breaker: `create.halt` in the state directory, one line `<config hash> <pending|posted>`, mode 600, written to `create.halt.tmp` and renamed under the run lock. The hash is `hash16` of the agent, environment, version and budget settings. A create trips it when its answer holds an id the bridge refuses, or when the session it answers does not fit the configuration it was made from (`session does not fit`): a session the bridge just made must fit, so one that does not is a response shape the bridge cannot read, and every later reply would replace it. While the file holds the current configuration's hash, the bridge creates and adopts nothing for a conversation without a fitting mapped session: it logs `create halted`, exits 2 and, once per halt (the `posted` mark), posts `the bridge cannot start a session that fits its configuration; check SOCK_BRIDGE_AGENT, SOCK_BRIDGE_ENVIRONMENT and SOCK_BRIDGE_BUDGET`. A mapped session that fits still serves. A file with another hash is removed on the next run, so fixing the configuration recovers by itself; deleting the file clears it too. A Check whose session does not fit trips the breaker too when the line's hash is the current configuration's (`session drifted`): a session made from this exact configuration that no longer fits is one the API now shows in a shape the bridge cannot read, so it is kept in the map, unused, instead of replaced on every reply. A different hash, or an unknown one, is the operator's change, and the session is replaced as below. So a shape mismatch costs at most one session whether the create answer or a later Check shows it; the live API's shape is still an open question.

Resolution, under the lock, before the `sent.ids` catch-up (which needs the session):

1. The conversation is in `sessions`: Check it, and use it while it lives and fits the configuration: `agent.id` is `SOCK_BRIDGE_AGENT`, `environment_id` is `SOCK_BRIDGE_ENVIRONMENT`, `agent.version` is `SOCK_BRIDGE_AGENT_VERSION` when that is set, and, when `SOCK_BRIDGE_BUDGET` is set, `budget.max_list_cost` is a `USD` amount of at most that many cents under a `budget.type` of `limit`. Agent, environment and a pinned version are exact; the budget is a cap, so raising `SOCK_BRIDGE_BUDGET` keeps every session, and a session with a higher budget, or none, while one is set does not fit. An unset version or budget is not compared.
2. It is not: Find, and adopt the newest session that fits the configuration as in step 1 (the agent id is compared here too, not left to the server's `agent_id` filter), whose `metadata.bridge_conversation` and `metadata.bridge_puppet` both match, whose `archived_at` is null and whose `status` is not `terminated` (`session adopted`). The list leaves archived sessions out by default (`include_archived` is false), and the bridge checks both fields anyway. This one path covers a crash between Create and the record, and a lost state directory. The list has no metadata filter, so the match is client side and bounded by the page cap; past the cap the bridge creates.
3. None found: Create, record, `session created`.

A mapped session whose Check answers 404 (deleted), or shows `status` `terminated` or a non-null `archived_at`, is gone (`session gone`): an archived session is `terminated` and takes no new events. Drop the line, resolve again from step 2 (which skips it), post the fixed text `the agent's earlier session ended; this reply started a new one`, then send. The owner learns that context was lost. A 404 on the stream or the send of a session the bridge created exits 1, so the retry checks again. With `SOCK_BRIDGE_SESSION`, 404 still exits 2: that session is the owner's, not the bridge's to replace. A mapped session that lives but does not fit the configuration (the operator changed the agent, the environment, the pinned version or the budget) is replaced the same way (`session config changed`), with the fixed text `the bridge configuration changed; this reply started a new session`: a configuration change never leaves a conversation on the old session. A session paused at its cap resumes when its budget is raised in the console within `SOCK_BRIDGE_BUDGET`; raised above it, the next reply replaces it (`session config changed`). To give it more, raise `SOCK_BRIDGE_BUDGET` first.

Trust: `bridge_puppet` is the bridge puppet's own `account.id` from the `whoami` the gate already runs, cached beside the owner id for the same minute, so two bridges on one agent never adopt each other's sessions. A `whoami` without an `account.id` UUID in this mode is `not a puppet token`, exit 2. Metadata is plain text at Anthropic: it carries ids, never the token or a hash of it, and never message text. The title carries 8 hex characters of the conversation id and nothing else.

Failure modes: a create that may have landed exits 1 and the retry adopts it (no duplicate session unless the list does not yet show it, see the open questions); a crash between Create and the `user.message` leaves an idle session that the retry adopts; a lost state directory costs one Find per conversation and loses nothing; two conversations racing cannot both create, because the lock serializes them; a crash after a gone session is replaced and before the notice is posted loses the notice, since the retry finds the new session mapped. Each session is billed on its own (runtime and its sandbox), so one per conversation costs more than one per bridge; the owner archives sessions in the console, and the bridge never archives or deletes. The map grows by one line per conversation and is never pruned. Budgets are per session ([session budgets](https://platform.claude.com/docs/en/managed-agents/budgets)): a session at its cap goes `idle` with `stop_reason` `budget_reached`, keeps its history and sandbox and is not terminated, so the bridge does not replace it and no reply gets a fresh budget that way. While it is at its cap the API refuses a `user.message` with a 400, so a reply exits 1 (`http 400`) until the owner raises its budget in the console, within `SOCK_BRIDGE_BUDGET` when that is set (removing the budget then makes the session not fit); a replaced session (gone or reconfigured) does start with a fresh `SOCK_BRIDGE_BUDGET`.

Tests (`test/bridge_sessions_test.go`, against the fake Managed Agents server's session endpoints): first use runs find, create, stream, send in that order with the exact create body, and records the line mode 600 with no `sessions.tmp` left; a second message reuses the session after a Check, another conversation gets its own; a dropped create exits 1 and the retry adopts without a second create; a lost state directory adopts the one live session of this conversation and puppet across pages, past archived, terminated, other-puppet, other-conversation and bad-id sessions; Find stops at 10 pages and creates; a second puppet on the same agent creates its own; a mapped session that is 404, terminated or archived is replaced, the other conversations' lines kept, the owner told before the answer; a 404 on the turn exits 1; create 400 and 404 exit 2, 500 and a dropped connection exit 1 with exactly one create, 429 is retried; a malformed create id exits 2 and records nothing; a create with a refused id, or one answered without the budget it was sent, trips the breaker, so 6 messages each delivered twice make one create, one Find and one halt notice; a Check that shows a correctly created session without its budget trips it too, so 4 messages make one create, one halt notice and one `user.message`, and the session stays mapped; a line's hash tells a changed budget (replaced) from drift (halted); and every run exits 2 with `create halted`; a changed configuration or a deleted `create.halt` clears it, and a mapped session that fits still serves while it holds; a budget whose type is not `limit` does not fit; a mapped session of another agent, environment or pinned version, or a budget above the configured one or none, is replaced with the configuration notice, a budget within it is kept, and an unset version or budget is not compared; Find adopts only a session that fits, a lower budget included, and checks the agent itself; an unreadable map exits 1 with no request and keeps every line; no key in curl's argv, any child's environment, the log or a state file, and no key, token, text or owner id in the create body; every setting's validation, and both modes together, exit 2 with no request; the puppet id is cached with the owner.

### Owner-brokered tool confirmations (integrations-0ga)

Built. Before this, `requires_action` posted a fixed text and the owner answered in the console. Now the owner answers from sock. Sources: [permission policies](https://platform.claude.com/docs/en/managed-agents/permission-policies) ("Respond to confirmation requests", "See how each call was evaluated"), [events and streaming](https://platform.claude.com/docs/en/managed-agents/events-and-streaming) ("Answer tool calls that pause the session", "Confirm a tool call"), and the API reference for [send](https://platform.claude.com/docs/en/api/beta/sessions/events/send) and [list](https://platform.claude.com/docs/en/api/beta/sessions/events/list) events.

The API's side: a call evaluated `ask` (an `always_ask` policy, or `auto` with no determination) is emitted as `agent.tool_use` or `agent.mcp_tool_use` with `evaluated_permission: "ask"` (`name` on both, `mcp_server_name` on the MCP one); the session goes idle with `stop_reason.type: requires_action` and the blocking ids in `stop_reason.event_ids`, and waits indefinitely. The answer is `POST /v1/sessions/$SESSION/events?beta=true` with `{"events":[{"type":"user.tool_confirmation","tool_use_id":<event id>,"result":"allow"|"deny","deny_message":<text>}]}`. `tool_use_id` is 1 to 128 characters; `deny_message` is allowed only with `deny` and is at most 10000 characters; several confirmations may go in one request. A confirmation for a call not evaluated `ask` is a 400, so the bridge can never override a server `deny`; the docs do not say what a second confirmation for a call already answered gets. Answering fewer than all blocking calls re-emits `session.status_idle` with the remainder; when every one is answered the session runs again. The listed history carries `user.tool_confirmation` events with their `tool_use_id` (the list schema; not checked against the live API).

The rule: a call is approved only by a whole owner message of the form `approve <code>`, where the code is one the bridge made for that call and the session never saw. Text that merely reads as approval approves nothing.

State: `confirm.pending` in the state directory, one line per call waiting on the owner, `<code> <conversationId> <session id> <tool_use_id> <pending|sent> <message id|-> <tool|?> <server|?> <since>`, mode 600, read and rewritten only under the run lock, through `confirm.pending.tmp` and a rename, at most 50 lines, `sent` ones counted. No line is ever evicted, another session's least of all: one turn gets at most 20 new codes, and calls past either bound are not asked (Asking, step 4). `<since>` is when the line took its state (epoch seconds): made pending, or marked `sent`. Each time the file is read under the lock, a `sent` line older than 24 hours and a pending line older than 7 days are dropped, so neither a run that never finished nor an abandoned session holds room for good. A dropped pending call can still be answered in the console; `approve` with its code gets `no approval is pending with that code`. A line with no `<since>` (written before lines had one) counts as made now. A code is never in a process's argv, where other local users can read it (`/proc/*/cmdline`): awk and jq get codes in their environment (`BRIDGE_CODE`, `BRIDGE_CODES`), which only this user can read, and a line is split by the shell, not through a here-document. Every match on it is made on text: awk compares two strings that read as numbers as numbers, and `10` and `1e1` would be one call.

Asking, at the end of any turn followed from the stream or the history:

1. The reducer keeps each `agent.tool_use`, `agent.mcp_tool_use` and `agent.custom_tool_use` of the turn by id (type, `name`, `mcp_server_name`, `evaluated_permission`) beside the `agent.message` text, and the ids of `stop_reason.event_ids` at the idle, each once (an id listed twice is one call with one code). Nothing else of a call is kept, its input never.
2. At `requires_action`, for each blocking id: a call this session already holds a line for keeps its code (an idle re-emitted after a partial answer, or a redelivery). A call evaluated `ask`, of the turn, with an id matching `[A-Za-z0-9_-]{1,128}`, gets a code: 6 characters of `a-km-z2-9` read from `/dev/urandom` (512 bytes through `tr -dc`, so each character is uniform), unique among the codes in the file. Anything else (an `agent.custom_tool_use`, a call evaluated otherwise, an id not seen in the turn, an odd id, no ids at all) cannot be answered from sock: the turn ends as before with `the agent is waiting for approval of a tool call`, no new line, and the owner answers in the console. Lines of this session for calls it no longer waits on are dropped.
3. The lines are written before anything is posted, so a code exists before the owner sees it.
4. Post the requests as a message of their own, first: per call of this conversation still pending, `the agent wants to run <tool>: reply "approve <code>" or "deny <code> <optional reason>"`, with ` from <server>` after the tool for an MCP call. Calls past the bounds (20 new codes a turn, 50 lines) get no code; the message ends `<n> more tool calls wait for approval: answer them in the Managed Agents console`. Then the agent's text so far, split as any answer, within the same 5 parts. So no cut of the agent's text can drop a request, and a request is never in the same message as the agent's text, which could otherwise dress itself as one. A tool or server name outside `[A-Za-z0-9_.-]{1,64}` shows as `a tool` and no server. The input is never shown (it can hold secrets, as everywhere in the bridge).
5. Record the message `replied`, log `approval requested`, exit 0. When the turn followed a confirmation and every call it waits on already has a line, the post is `recorded; <n> more waiting` instead (`approval recorded`).

A turn that ends any other way (`end_turn`, `budget_reached`, `session.error`) drops every line of its session: the session waits on none of them.

Answering, for an owner message that passed the gate:

1. Parse the text, trimmed of surrounding spaces, tabs and newlines. `approve` (ASCII case-insensitive) and one space and a code of `[a-km-z2-9]{6}` must be the whole message. `deny`, a space and a code may be followed by whitespace and a reason. The code itself is case-sensitive; no other spacing, quoting or prefix counts.
2. A message that parses is looked up before the session is resolved, by code and conversation: a line marked `pending`, or marked `sent` by this same message id. Anything else posts `no approval is pending with that code` and exits 0 (`approval not pending`). So a code binds to one conversation, one session and one call, and a code another message sent is not pending.
3. After the session is resolved, a line whose session is not the current one is dropped (`that approval is no longer pending`, `approval refused`). Then the history is read for a `user.tool_confirmation` of that `tool_use_id`. Found on a line marked `sent`: a crash after the POST, so the turn is followed from the history and nothing is posted again. Found on a `pending` line: answered in the console, so the line is dropped and the owner told `that approval is no longer pending` (`approval refused`).
4. Otherwise open the stream, mark the line `sent` with this message id (before the POST, the `sent.ids` rule), and POST the confirmation. A deny reason is cleaned of control characters other than newline and tab (and of the bidi and separator characters, as the answer is), every code in `confirm.pending` replaced by `[code]` as the scrub matches it (below), the reason's other characters left as they are (an emoji's joiners, right-to-left marks, soft hyphens), cut to 1000 bytes on a character boundary and trimmed; `deny_message` is sent only when something is left.
5. A 400 drops the line, posts `that approval is no longer pending`, exits 0 (`approval refused`). A 2xx: follow the stream as a turn whose anchor is this `user.tool_confirmation` (the reducer's `$tuid`; an end before it is `stream unanchored` and finishes from the history, as for a `user.message`). The turn ends as any other: with an answer, or at an idle re-emitted with the remaining calls (`recorded; <n> more waiting`), or at a new `requires_action`. The line stays `sent` until the turn ends, so a redelivery after a crash finds it; the end drops it.
6. An ordinary reply (one that does not parse) while this session has lines: the history says what the session still waits on (the last status event is a `requires_action` idle, less the calls confirmed after it). Lines for calls it no longer waits on are dropped. With any left, the reply is not sent into the session: the bridge posts `a tool call is waiting, so this reply was not sent to the agent:` and the pending requests of this conversation (or, with none, that the call waits in another conversation or the console), records the message `replied`, exits 0 (`approval pending`). With none left, the reply goes in as usual. A redelivered message whose `user.message` already went in skips this check.
7. An ordinary reply that goes into a session, in any conversation, first has every code in `confirm.pending` replaced by `[code]`, as the scrub matches it. A code quoted in conversation B never reaches B's session.

The scrub, for a deny reason and an ordinary reply alike, folds for matching only and changes no other text: each character of a code matches itself in either case and its fullwidth forms (U+FF01 to U+FF5E), and may be followed by format characters (`Cf`, U+200B among them) and combining marks (U+0300 to U+036F). Residual, accepted: a code spelled with spaces between its characters, precomposed accented letters (U+1E93 for `z` with a dot below) or homoglyphs from other scripts passes through. Recovering a code that way gives the agent nothing, since only the owner passes the gate, and only the owner can have typed it.

Trust boundaries:

- Only the owner: the existing gate, unchanged. The agent's own text cannot approve: it reaches sock only as the bridge puppet's messages, and the puppet is never the owner. An MCP server on the session that could message sock as some account still fails the gate.
- Not text that looks like approval: the code is made by the bridge, held only in the state directory and in messages to the owner, never sent into the session (an ordinary reply or a deny reason that quotes one has it replaced), never in a request, never in argv and never logged, so neither the agent nor anything it reads can produce a valid one. A forged confirmation request in the agent's answer carries a code that is not pending.
- Replay: a redelivered `approve` is a `duplicate` by `done.ids`; a used code is gone once its turn ends, and while its turn runs it counts only for the message that sent it; an approval for a call answered elsewhere is found in the history or refused by the API.
- The deny reason is owner text that reaches the agent as a tool result. It is data, like a `user.message`, but it is not wrapped in the `<sock-message>` tag, because the API places it; the cut and the cleaning bound it.
- The log names the outcome, never the code, the tool name, the input or the reason.

Failure modes: a crash after the POST repeats nothing (step 3 finds it in the history); a crash between the POST and the line marked `sent` cannot happen, since it is marked first, and a crash after marking it and before the POST posts it on the retry; a crash after the lines are written and before the request is posted posts it again with the same codes; a lost state directory loses the codes, so an `approve` is refused and the owner answers in the console (fail closed); a confirmation that never comes leaves the session waiting, as the API allows, and costs nothing while idle. If the API took a second confirmation of a call answered in the console without a 400 in the moment between the history read and the POST, the turn it waits for has already run, and the run ends at the timeout and its retries.

Out of scope: confirmations raised while the session stays `running` (a workflow run's calls, which carry `evaluated_permission: "ask"` without an idle); the bridge waits for idle and times out. Custom tools: the bridge has none to run.

Tests (`test/bridge_confirm_test.go`, against the fake Managed Agents server, which plays tool events, `requires_action` idles and echoes `user.tool_confirmation`): a request shows the tool name and a code but not the input, the line is mode 600 with no tmp left, and the code is in no request the API got and not in the log; codes are fresh and in the alphabet; `approve` posts `allow` with the `tool_use_id` and no `deny_message`, follows the turn (also when the stream does not echo the confirmation), drops the line, a redelivery is a duplicate and the used code is refused; `deny` sends a reason cleaned, stripped of the code and cut to 1000 bytes, and none without one; a non-owner and the bridge puppet are dropped; look-alikes (a prefix, a suffix, a quote, two spaces, a tab, two lines, an upper-case code, a Cyrillic letter, the bridge's own request text) approve nothing and are held; a wrong code and a code of another conversation are not pending; an ordinary reply is held while the history shows the session waiting and goes in once it does not; a call answered in the console is not posted; a 400 drops the line; a crash after the POST repeats nothing; a code sent by one message approves nothing for another; two calls are answered one by one with `recorded; 1 more waiting` between; a custom tool, an unseen, odd, too long or not-ask id, no ids and a call before the turn keep the fixed text; an odd tool name shows as `a tool`; a turn read from history asks too; one turn asks at most 20 calls; a turn never evicts another session's lines, and with the file full asks nothing and notes the calls for the console; sent lines count toward the bound, and one older than 24 hours is dropped; 50 pending lines older than 7 days are dropped, a new call is asked and an old code answers nothing; a line with no time is kept and stamped; codes and call ids are matched as text; the requests are the first message, alone, even after an agent text that fills five parts; a deny reason loses every code in upper case, fullwidth, with combining marks and split by U+200B, U+00AD or a tag character, and one with no code keeps its emoji joiners, right-to-left marks and soft hyphens intact; an ordinary reply quoting a code in fullwidth or with combining marks reaches its session as `[code]`; an ordinary reply in another conversation quoting a code in any form reaches its session as `[code]`; no code is in any argv (awk, sed, jq, curl and the other tools wrapped to record theirs) across an ask, a held reply, a deny and an approve; an id listed twice gets one code.

### Follow-up: webhook delivery (integrations-lcn)

Won't build. Managed Agents does have webhooks ([webhooks](https://platform.claude.com/docs/en/managed-agents/webhooks)), but they do not fit a `sock listen --exec` command, and what they would replace (one stream held for one turn) is cheap.

What the API offers: an endpoint registered in the Console per workspace, not per session; HTTPS on port 443 with a publicly resolvable hostname (a non-public address disables it); events such as `session.status_idled` that carry only `type` and the session `id`, so the receiver must still GET the session and list its events; `webhook-id`, `webhook-timestamp` and `webhook-signature` headers with a `whsec_` secret, verified by the SDK's `unwrap()` with a 5 minute freshness check; at least once, unordered, at most three attempts over about two minutes, then dropped with no signal; nothing is replayed while an endpoint is disabled.

Why not:

- Shape. `sock listen --exec` runs a command per sock message. A webhook needs a long-lived HTTP receiver on a public HTTPS name: a daemon, TLS, a tunnel or a host, a second secret to store and a process to keep alive. That is a service, the thing this bridge exists to avoid (rookery scaffold, deploy, monitoring), on a user's machine that is usually behind NAT.
- Ack. Today the ack is the exit code after the answer is posted. With webhooks the command would exit after the `user.message` and the answer would arrive later in another process, so a dropped webhook (three tries, then silence) loses the answer unless something lists sessions to reconcile. That reconcile is a poll on a clock, and it is the history catch-up the bridge already has.
- Gain. The stream costs one open connection for the length of a turn, inside the timeout. Webhooks would free the `listen` stream during long turns, which the queue on Anthropic's side and the timeout already bound.

If revisited (the bridge hosted next to `sock-mcpd`, which has a public HTTPS name and runs as a service), the receiver would: verify the signature over the raw body with the SDK, in constant time, refusing a stale timestamp; deduplicate on `webhook-id`; bind each event by checking `data.workspace_id` against the configured workspace and `data.id` against the bridge's own session map, dropping anything else; never trust payload content, only GET the session and its events; and keep the history catch-up as the source of truth for any idle it missed. Not designed further.

### Follow-up: open questions

- Open: whether `GET /v1/sessions` lists a session immediately after its create returns. If not, a crash right after Create can make a second session; the bridge would need a short Find retry before creating. Not checked against the live API.
- Open: whether a `user.message` sent while the session waits on `requires_action` is rejected or queued. The docs say only that a `system.message` sent alone or with a `user.message` is rejected until the pending calls are resolved. The bridge refuses to send one (Answering, step 6); if the API queues it, forwarding with a note is an alternative.
- Open: whether the owner sees the tool input in a confirmation request. Withheld because inputs can hold secrets and leave Anthropic only for sock; an opt-in (`SOCK_BRIDGE_SHOW_TOOL_INPUT=1`, cleaned and cut to 2000 bytes) would make the approval informed. The owner decides.
- Settled by the API reference, not yet by the live API: the listed history carries `user.tool_confirmation` with its `tool_use_id` (Answering, step 3, relies on it), and a partial answer re-emits the idle with the remaining calls (step 5).
- Open: whether `approve all` for a turn with several pending calls is worth its risk (one message approving calls the owner did not read).
- Open: archiving. Sessions created per conversation accumulate; the bridge never archives. An idle sweep would be a clock; leaving it to the owner is the current answer.

## Tests

Under `test/`, against stubs of `sock` (whoami output, listen environment) and of `claude` and `codex` that record argv, environment and stdin: the owner's message runs the agent exactly once with the text on stdin and in neither argv nor environment; a non-owner sender, a mismatch between env and stdin sender, malformed JSON and a missing field are dropped with exit 0 and no agent run; a failing whoami exits 1 with no agent run; an owner id is cached for a minute and a non-owner costs no call; a human token exits 2 with nothing acknowledged; the allowed tools equal the plugin-derived names; a redelivered id does not rerun; a stale lock whose pid was reused is replaced; a bad configuration exits 2; a second runner waits on the lock, a stale lock is replaced by exactly one of two racing runners, and a lock whose pid file is still being written is never taken (the lock is one symlink, so there is no such window); a non-UUID `id` or `conversationId` is dropped with exit 0 and never reaches the agent; the timeout kills grandchildren of the agent too (a stub agent that spawns a long `sleep` leaves none); the agent's environment holds no `SOCK_TOKEN` or `SOCK_URL` for `claude` and does for `codex`; a log directory that cannot be written still exits with the agent's status; the timeout kills the agent and exits 1; the log never contains the text or the token; `</sock-message>` in the text cannot close the tag; `bypassPermissions` and `danger-full-access` are refused without `SOCK_RUNNER_ALLOW_BYPASS=1`.

Security review before merge, as the review gate below: sender spoofing, injection through the text into argv, environment or the tag, lock races and stale locks, log leakage, and any path where a non-owner message reaches the agent.

## Hosted connector: ChatGPT, dots and claude.ai

The public listing in the OpenAI plugin directory and the claude.ai connector both take a remote MCP server behind OAuth 2.1, and the directory refuses plugins with hooks. The design is split ([ADR 11](https://github.com/aeryx-ai/sock-contract/blob/main/docs/adr/0011-agent-platforms-connect-through-oauth.md) in `sock-contract`): the authorization server and the connector grant live in `sockd`'s Identity context on `api.sock.aeryx.ai`; the resource server is `sock-mcpd` on `mcp.sock.aeryx.ai`, specified in [connector](connector.md). This repository owns the client side:

- **Client registration.** ChatGPT and Claude arrive by CIMD, so no secrets are exchanged; redirect URIs come from their metadata documents (`https://chatgpt.com/connector_platform_oauth_redirect` because the hub implements RFC 9207, `https://claude.ai/api/mcp/auth_callback`, loopback for Claude Code). Others register by DCR.
- **The directory package** is a second plugin, separate from the Codex marketplace one (which keeps hooks for manual installs): `skills/sock/SKILL.md` plus a remote MCP entry for `https://mcp.sock.aeryx.ai/mcp` with auth mode `cimd`, every tool declared `oauth2`, no hooks, and the listing metadata under `extensions.com.openai.interface`: display name, the subtitle (at most 30 characters), long description, developer name, category, a square icon of at least 48 px, website, support, privacy and terms URLs. The domain challenge is served by `sock-mcpd`. Submission needs the owner's business verification, five positive and three negative test cases, a demo video, release notes and a reviewer account: a dedicated sock human on production whose connector puppet the consent flow creates, with no MFA. Servers are rescanned daily, so a tool change is a release.
- **Dots.** The user tells the dot to watch sock replies; whether the dot or ChatGPT creates the `owner.reply` subscription is settled by the live dot test and written into the install notes.
- **claude.ai.** The same URL as a custom connector; `oauth_cimd` works without a registration call. Outbound only in v1; Claude Code keeps the stdio plugin and its channel.
- **Testing, in order**: tool discovery over OpenAI's Secure MCP Tunnel with the stdio server; the staging endpoint as a custom MCP server in ChatGPT developer mode and as a claude.ai connector; an owner reply arriving at a dot; then submission. The production plugin stays private, installed from this marketplace with the hosted URL, until the directory approves.

## Project puppets: the machine key

One puppet per machine breaks with more than one Claude Code session: the hub's delivery queue is per puppet, so sessions compete for the owner's replies. The product owner's requirements: setup in one step, and every message shows who sent it. [ADR 10](https://github.com/aeryx-ai/sock-contract/blob/main/docs/adr/0010-machine-keys-mint-project-puppets.md) in `sock-contract` gives the hub a **machine key** (`sock_mk_`): a human's device that may only create, list, mint tokens for and erase the puppets it created. This repository's part:

- The plugin's `userConfig` keeps one `sock_token` option (sensitive, required, titled "sock machine key or puppet token" since plugin 0.3.2) that takes either credential; `sock_url` stays. `notify_on_stop` was removed in plugin 0.3.8: the hooks send only the ask and permission prompts (notify.sh rule 8d). This amends the earlier plan of a separate `sock_machine_key` option: one option means a `sock_token` already set keeps working, as one puppet for the machine, until the owner pastes a machine key in its place.
- `sock-mcp` (the `mcp` repository) mints one puppet per project on first use, named `<project> on <host>`, where the project is the repository name (every worktree of a repository shares its puppet) or the directory name outside git; on `PUPPET_NAME_TAKEN` it appends a short hash of the path. It keeps each token at `${XDG_STATE_HOME:-~/.local/state}/sock-integrations/puppets/<key>` (mode 600) beside the repository path, and on start erases puppets whose repository is gone.
- `hooks/notify.sh` sends as the project's puppet: it asks the `sock` CLI for the project's token (`sock puppets ensure <dir>`, which reads the same cache or mints), so the hook and the server always agree. The ensure-or-read routine lives once, in `sock-client`.
- `SKILL.md` and the README say what the owner sees: a contact per project, erasable from the app like any puppet; `sock puppets use` stays for Codex and the tunnel.
- Each diff that touches the key (hub, `sock-mcp`, this plugin) gets a fresh-context security review before merge.

## Review gates

This repo handles a secret and an agent-to-human trust boundary. Before merge, a fresh-context subagent reviews the diff for token leakage (logs, process list, config files), fail-open paths and prompt injection through the inbound path, and each finding is verified against the build.

## Decisions

- Shell hook over a Go binary: the hooks send fixed text, the matcher already splits the cases, and the `sock` CLI is the existing client. A binary would add a module dependency on `sock-client` (not yet tagged) for no gain.
- Async plus a self-bound over a host timeout: the host does not enforce `timeout` on async hooks, and a synchronous permission hook would delay the agent whenever sock is down.
- Fixed phrase over forwarding `message` (superseded 2026-10-13): the fixed phrases told the owner nothing, so the hooks now forward the notification text and the trailing ask of the last assistant message. The residual risk, text the assistant echoed leaving the machine, is accepted by the owner; code blocks are dropped and the ask is capped at 600 bytes.
- Plugin `userConfig` for the token: secure storage, one prompt, and hooks and the MCP server both receive it without a file.
- The runner runs as a user service (2026-10-14, the orchestrator for the product owner): the product requirement is that nothing needs babysitting, and a `sock listen` started by hand dies with its terminal, a reboot or a logout. This supersedes "No service means no rookery scaffold" for the runner. Still no daemon of this repo's: the OS service manager supervises the CLI's `sock listen`, which keeps reconnect, backoff and ack-on-exit; launchd and systemd add restart and start-at-login. Rookery's daemon+CLI shape does not fit a unit that only runs an existing command.
